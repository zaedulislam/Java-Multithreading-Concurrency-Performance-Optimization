# Resource Sharing between Threads
Let's define what we mean by a resource and get some motivation on why we want to share resources between threads in the first place.

### What is a resource?
A resource in the scope of a computer program is something that represents data or a state. These can be simple variables such as integers or strings,
data structure objects such as arrays, collections, or maps, objects that represent files, connections to the network or databases, message queues, 
or really any object that we create.

### What resources can threads share inside a process?
It's everything we store in the heap. Objects, everything inside objects and static variables. As a side note, everything outside the process is also 
shared between threads, but that's outside of the scope of this note.


### Why do we want to share anything between threads in the first place?
First, let's get some motivation with a few examples before we get anywhere too deep.

### Example 1
Let's assume that a text editor that has two threads, one that responds to keyboard and mouse events and represents the document's current view on the screen, 
and another runs once in a few seconds and saves the document to the disk. Both threads have access to the same data structure that represents the document in 
the memory. That data structure is a shared resource. In this case, the benefit from sharing this data structure is that the document saver thread can save the 
user from losing his or her work if the application crashes, or if we lose power, for example.

### Example 2
Another very typical multithreaded software architecture design is having one thread called the dispatcher thread that takes work as an input either directly 
from the user or through HTTP requests. If it's a web server, for example, and distributes the work among a small number of dedicated worker threads using a 
shared queue. The worker threads are waiting for the work to arrive through that queue and grab the task from it as soon as they finish their current task.
That queue here is obviously backed by a data structure stored on the heap, and is a shared resource. This leads to very efficient CPU utilization and low latency, 
as we don't need to recreate a new thread every single time we have a new task. So high performance is a clear benefit in this case.

![](https://github.com/zaedulislam/Java-Multithreading-Concurrency-Performance-Optimization/blob/main/images/image_5.5.png)

### Example 3
Last example to get us motivated would be another very typical multi-threaded software architecture used in backend services, where we have a microservice 
that acts as a software abstraction layer on top of a database. Every request is handled by a different thread, but eventually all requests become 
either reads or writes from or to a database. The connection to that database is represented by an object or a set of objects, which are again shared 
by all the request threads. In this case, we absolutely have to have this shared connection as we have only one database, but there are many independent 
requests coming in all the time.
